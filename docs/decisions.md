# Технічні рішення

Формат: рішення, причина, наслідки. Нові рішення додаються вгору списку.

## D-20. Контрольне розширення `GET /health/dependencies` крізь усі шари (ЛР5)

- **Рішення:** додано `GET /health/dependencies`, який через `Depends` викликає `PredictionService.check_dependencies()`, звертається до `TeamStatsProvider.list_teams()` і повертає `200 OK` або `503 Service Unavailable` через `error_handlers.py`.
- **Причина:** перевірити проходження запиту крізь усі шари архітектури (`router → service → provider → error_handlers`).
- **Наслідки:** додано `DependencyHealthResponse` та 4 автотести у `tests/test_health_dependencies.py`.

## D-19. Перевірка HTTP-шару через `TestClient` + `dependency_overrides` і golden-тести (ЛР5)

- **Рішення:** зафіксовано регресійний еталон (`tests/test_golden_regression.py`), а HTTP-шар перевірено через `fastapi.testclient.TestClient` і `app.dependency_overrides` (`httpx` у `requirements-dev.txt`).
- **Причина:** у ЛР3 тести викликали функції напряму без HTTP-серіалізації та обробників помилок.
- **Наслідки:** `requirements.txt` залишився мінімальним, 19 автотестів покривають домен, сервіс і HTTP-відповіді `200 / 400 / 404 / 503`.

## D-18. Централізована конфігурація через змінні середовища (ЛР5)

- **Рішення:** створено `app/core/config.py` (`Settings`, `get_settings()`), де `STATS_PROVIDER`, `WEIGHT_WIN_RATE`, `WEIGHT_RATING` і `CORS_ALLOW_ORIGINS` зчитуються зі змінних середовища.
- **Причина:** винести налаштування з коду маршрутів та сервісу без втрати нульової конфігурації за замовчуванням.
- **Наслідки:** провайдер, ваги моделі та CORS змінюються без редагування коду.

## D-17. Централізоване перетворення доменних помилок на HTTP-статуси (ЛР5)

- **Рішення:** `PredictionService` кидає доменні винятки (`SameTeamsError`, `TeamNotFoundError`, `StatsUnavailableError`), а `app/api/error_handlers.py` перетворює їх на JSON-відповіді `400`, `404`, `503`.
- **Причина:** відокремити бізнес-логіку від `fastapi.HTTPException` та уніфікувати формат помилок.
- **Наслідки:** `PredictionService` тестується без FastAPI.

## D-16. Шарувата архітектура backend і порт `TeamStatsProvider` (ЛР5)

- **Рішення:** монолітний `backend/main.py` розділено на `app/domain`, `app/services`, `app/infrastructure/providers` (`InMemoryTeamStatsProvider`, `FakeTeamStatsProvider`), `app/api` та `app/schemas.py`. Кореневий `main.py` став тонкою точкою входу.
- **Причина:** ізолювати джерело статистики за контрактом `TeamStatsProvider` для підключення реальних API без зміни бізнес-логіки.
- **Наслідки:** запуск `uvicorn main:app --reload` працює як раніше; підміна провайдера виконується через `STATS_PROVIDER=fake` або `Depends`.
## D-15. Екрани перемикаються станом, без бібліотеки навігації (ЛР4)

- **Рішення:** `AppRoot` тримає поточний `Screen` (`Predict`, `History`, `Details`). Системна кнопка «Назад» обробляється через `BackHandler` на екранах історії та деталей. Вибір команд на головному екрані зберігається `rememberSaveable`.
- **Причина:** не додавати нових залежностей заради трьох екранів.
- **Наслідки:** результат прогнозу на головному екрані не зберігається при переході в історію (лишається в історії). Для більшої кількості екранів потрібна бібліотека навігації.

## D-14. Збереження лише після успішної відповіді, збій бази не ховає результат (ЛР4)

- **Рішення:** `HistoryStore.add()` викликається тільки після того, як `ApiClient.predictMatch()` повернув відповідь без винятку; додатково `isSavable` відхиляє порожні назви й ймовірності поза 0..1. Виклик обгорнуто окремим `try/catch`.
- **Причина:** методичка вимагає не зберігати помилки та неповні відповіді; користувач не повинен втрачати отриманий результат через збій локальної бази.
- **Наслідки:** запис створюється в єдиному місці (після успіху). Збій запису мовчки пропускається, див. `known-limitations.md`.

## D-13. Повна відповідь зберігається JSON-рядком у `details_json` (ЛР4)

- **Рішення:** окремі колонки лише для списку (`input_summary`, `result_summary`, `status`, `created_at`), а повна відповідь backend (15 полів) в одній колонці.
- **Причина:** API вже виросло з 5 до 15 полів, і зміна схеми бази при кожному розширенні була б зайвою; деталі мають показувати той самий розрахунок, що був на момент запиту, без нового виклику AI.
- **Наслідки:** по полях розрахунку не можна шукати чи фільтрувати. Перейменування полів `PredictResponse` ламає читання старих записів.

## D-12. `SQLiteOpenHelper` замість Room (ЛР4)

- **Рекомендація методички:** Room, допускається інше постійне сховище.
- **Рішення:** вбудований у Android `SQLiteOpenHelper` (локальна база SQLite). Нових залежностей і змін у `build.gradle.kts` та `libs.versions.toml` немає.
- **Причина:** Room потребує плагіна KSP, версія якого має відповідати зв'язці AGP 9.4.0 і Kotlin 2.2.10. Збірка Gradle в цьому проєкті вже була ризикованою (так само відмовились від Retrofit і Ktor, D-4). За правилом `ai-instructions.md` нова залежність потребує обґрунтування, а вигода від Room для однієї таблиці невелика.
- **Наслідки:** запити пишуться вручну, версія схеми 1, міграцій немає. Операції відокремлені від інтерфейсу в `HistoryStore` і виконуються у `Dispatchers.IO`. Перехід на Room можливий пізніше без зміни екранів.

## D-11. Розбивка розрахунку: плоскі поля з префіксами, `explanation` збережено (ЛР3)

- **Рішення:** десять нових полів додано до `PredictResponse` на тому ж рівні (`team_a_win_rate`, `team_a_rating`, `team_a_win_rate_contribution`, `team_a_rating_contribution`, `team_a_score` і так само для `team_b_`). П'ять полів ЛР2, зокрема `explanation`, не змінено.
- **Причина:** сумісність зі старим клієнтом і простота ручного розбору JSON в `ApiClient.kt`: нові значення читаються тими ж викликами `getDouble`, що й старі.
- **Наслідки:** відповідь має 15 полів. Вкладені об'єкти (наприклад, `team_a: {...}`) були б охайнішими, але вимагали б переписати розбір. Нове поле треба додавати синхронно в Pydantic, `ApiModels.kt`, `ApiClient.kt` і `api-contract.md`.

## D-10. Розрахунок винесено в чисту функцію `calculate_prediction()` (ЛР3)

- **Рішення:** формула з `predict()` перенесена у функцію, яка приймає назви та статистику двох команд і повертає `PredictResponse`. Endpoint `predict()` лише перевіряє команди й викликає її.
- **Причина:** у `TEAMS_DB` немає пар із рівними округленими ймовірностями, тож гілку «рівні шанси» неможливо перевірити через реальні дані. Чиста функція дозволяє передати синтетичну статистику в тесті.
- **Наслідки:** це єдиний рефакторинг у ЛР3. Формула, ваги 0.6 / 0.4, поведінка 400, 404, 422, `TEAMS_DB` і CORS не змінились. Ймовірності рахуються з незаокруглених балів, тому відсотки лишились 53% / 47%.

## D-9. Тести backend на стандартному `unittest`, без нових залежностей (ЛР3)

- **Рішення:** автотести написані на `unittest` і викликають функції `calculate_prediction()` та `predict()` напряму. Запуск: `python -m unittest discover -s tests -v` з папки `backend`.
- **Початковий план:** `pytest` і `httpx` (для `TestClient`). Замінено на пропозицію агента при розгляді плану, бо вона не додає залежностей.
- **Причина:** методичка вимагає обґрунтовувати нові залежності. `unittest` входить у стандартну бібліотеку Python, а прямий виклик функції не потребує `httpx`.
- **Наслідки:** `requirements.txt` не змінювався. Тести не перевіряють HTTP-шар, повну відповідь перевірено вручну через Swagger.

## D-8. Один репозиторій із папками `mobile/` і `backend/`

- **Причина:** методичка вимагає одного Git-репозиторію з обома частинами; той самий репозиторій використовується для ЛР1, ЛР2 і ЛР3.
- **Наслідки:** стани лабораторних позначаються тегами `lab1`, `lab2`, `lab3`.

## D-7. Відкритий CORS (`allow_origins=["*"]`)

- **Причина:** спрощує розробку. Мобільний застосунок не є браузером, тож для нього CORS не потрібен, це запас на майбутній веб-клієнт.
- **Наслідки:** для продакшену потрібен обмежений список джерел.

## D-6. HTTP замість HTTPS (`usesCleartextTraffic="true"`)

- **Причина:** локальний backend працює без TLS, а Android блокує HTTP за замовчуванням.
- **Наслідки:** допустимо лише для розробки.

## D-5. Доступ емулятора до backend через `adb reverse`

- **Рішення:** `adb reverse tcp:8000 tcp:8000` і адреса `http://127.0.0.1:8000`.
- **Причина:** стандартна адреса `10.0.2.2` давала timeout (`failed to connect ... after 5000ms`) на використаному образі емулятора.
- **Наслідки:** команду треба повторювати після перезапуску емулятора.

## D-4. `HttpURLConnection` і `org.json` замість Retrofit/Ktor

- **Початковий план:** Ktor Client.
- **Рішення:** вбудований `HttpURLConnection` у `Dispatchers.IO`.
- **Причина:** не потребує нових залежностей і змін у `libs.versions.toml`, менше ризик зламати Gradle-збірку.
- **Наслідки:** JSON розбирається вручну, нове поле додається в кількох місцях.

## D-3. Вагова формула замість ML-моделі

- **Рішення:** `score = win_rate·0.6 + rating·0.4`, ймовірність як частка від суми балів.
- **Причина:** методичка допускає базовий алгоритм і не вимагає навчання моделі. Обсяг доступних даних замалий для навчання.
- **Наслідки:** прогноз демонстраційний (див. `ai-component.md`). Формулу можна замінити, зберігши формат відповіді.

## D-2. Hardcoded `TEAMS_DB`

- **Причина:** MVP має показати повний потік mobile → backend → результат, а не інтеграцію з зовнішніми джерелами.
- **Наслідки:** дані демонстраційні. Список команд клієнт бере через `GET /teams`, тому назви завжди збігаються з довідником.

## D-1. Python, FastAPI, Pydantic для backend

- **Причина:** рекомендований методичкою стек. Pydantic дає валідацію, FastAPI дає автоматичний Swagger UI.
- **Наслідки:** запуск через Uvicorn, залежності в `backend/requirements.txt` (`fastapi`, `uvicorn`, `pydantic`).
